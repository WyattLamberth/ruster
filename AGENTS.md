# Repository Guidelines

## Project Structure & Module Organization

This repository is a small Rust learning project for reading and analyzing text files.

- `src/main.rs` contains the command-line application and currently holds all program logic.
- `src/practice.txt` is sample input for local runs.
- `Cargo.toml` defines the `ruster` package and Rust 2024 edition.
- `Cargo.lock` records the resolved dependency versions and should remain committed.
- `target/` is generated by Cargo and must not be committed.

Keep small exercises in `main.rs`. If the program grows, move reusable logic into `src/lib.rs` or focused modules under `src/`.

## Build, Test, and Development Commands

- `cargo run -- src/practice.txt` builds and runs the program with the included input file.
- `cargo check` quickly checks types and compiler errors without producing a runnable binary.
- `cargo build` creates a debug binary under `target/debug/`.
- `cargo test` runs all unit and integration tests.
- `cargo fmt --check` verifies standard Rust formatting; use `cargo fmt` to apply it.
- `cargo clippy -- -D warnings` runs additional correctness and style checks, treating warnings as failures.

Run formatting, Clippy, and tests before submitting changes.

## Coding Style & Naming Conventions

Follow standard Rust style and let `rustfmt` control layout. Use four-space indentation, `snake_case` for variables and functions, `PascalCase` for structs and enums, and `SCREAMING_SNAKE_CASE` for constants. Prefer focused functions and explicit error handling over unchecked `unwrap()` calls as the exercise develops. Keep comments useful and current; use `TODO:` for intentional follow-up work.

## Testing Guidelines

There are no tests yet. Add unit tests beside extracted logic in a `#[cfg(test)] mod tests` block. Put end-to-end CLI tests in `tests/` if introduced. Name tests by observable behavior, such as `counts_words_separated_by_whitespace`. Cover normal input, empty files, missing arguments, and unreadable paths. No numeric coverage target is currently required.

## Commit & Pull Request Guidelines

Existing commits use short, imperative descriptions, for example `Update input file with more text`. Continue that style and keep each commit focused on one logical change. Pull requests should explain what changed, why it changed, how it was verified, and any remaining TODOs. Link relevant issues when available. Include terminal output examples when command-line behavior changes; screenshots are unnecessary for this CLI project.

## Learning-Focused Contributions

This is a guided Rust learning project. When reviewing or assisting, explain concepts, ask leading questions, and provide incremental hints instead of dropping complete solutions unless explicitly requested.
